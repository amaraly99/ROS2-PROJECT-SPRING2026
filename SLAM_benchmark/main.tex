\section{Introduction}

In this report, OV$^{2}$SLAM (Accurate and Fast), ORB-SLAM2, ORB-SLAM3, and RTAB-Map are benchmarked on the EuRoC MAV sequences. The purpose of this benchmarking is to provide insights on the bottlenecks and accuracy drops because of this setup shift. The benchmarking was done on 10 of the EuRoC MAV (Micro-Aerial Vehicle) sequences, with MH being Machine Hall and V being Vicon Room. Do note that the evaluation setup was done in a way such that it replicates the research papers results.

\textbf{DISCLAIMER}: The experiments in this report are not fully reproducible (numbers-wise) due to the frequent failures and varying results experienced when running SLAM algorithm. A hypothesis for this would be the different CPU runtime conditions, thread scheduling, missing frames, and non-seeded random actions. ORB-SLAM3 and the OV$^{2}$SLAM variants mostly report \textbf{best-run} RMSE (closest to paper values after reruns). ORB-SLAM2 (batch \texttt{20260530\_232822}) and RTAB-Map report \textbf{mean$\pm$std} over repeated runs. Red sequence names mark known weak spots (often ORB-SLAM3 instability).

\section{Hardware Details}
All Experiments were ran on the Raspberry PI 5 with 16GB Memory. All Sequences were ran several times (on ORBSLAM2 and RTAB-Map) and the best RMSE for a sequence is defined as the RMSE that is the lowest but the path length is close to ground-truth length. 

\section{Algorithm Implementation Details}

The OV$^{2}$SLAM code was taken from its original source GitHub implementation and benchmarked directly in its ROS2-based form, with only limited changes required to support the experimental setup used in this work. In other words, OV$^{2}$SLAM already provided a ROS-ready code, so it was evaluated more directly than ORB-SLAM3.

ORB-SLAM2 was evaluated through the local \texttt{ros2-ORB\_SLAM2} wrapper (stereo node, EuRoC YAML, automated shutdown). It needed less surgery than ORB-SLAM3 but still needed ROS2 bag bridging and timing/CPU hooks matching the other pipelines.

RTAB-Map was evaluated through its native ROS2 launch pipeline with EuRoC-aligned stereo inputs, rosbag playback under simulated time, and the same external timing/CPU instrumentation used for the other systems. It integrated more smoothly than the ORB-SLAM wrappers, but still needed careful topic/remap alignment and controlled shutdown to keep runs reproducible.

However, ORB-SLAM3 was messier as the original source code does \textbf{NOT} provide a ROS implementation, and rather reliance on community-maintained github repositories was necessary. Most repositories are ROS wrappers over the original ORB-SLAM3 code, despite this, the codebase iwht the following URL \url{https://github.com/Mechazo11/ros2_orb_slam3/tree/jazzy} was used as the base ROS2 Jazzy ORB-SLAM3. However, this codebase was only a starting skeleton (according to the github) and required extensive modification to make it suitable for benchmarking in the target environment.

Modifications to ORB-SLAM3 ROS2 were needed in order to allow for smooth benchmarking.
The modifications one where:
\begin{itemize}
    \item fixing hard-coded paths, correcting YAML and package path handling, resolving build and dependency issues related to Pangolin
    \item fixing the code tendency to use streamed images rather than a bag file, by subscribing to the topic of images
    \item adding Stereo mode, since the current github does \textbf{NOT} include it
    \item inplementing a shutdown ACK-based sequence to allow for automated shutdown instead of manual CTRL+C
    \item disabling autoAbortLBA when a new keyframe arrives because there was a case where the BA completed 44\% of its iterations, which was one of the major causes of high RMSE
\end{itemize}

\subsection{RTAB-Map Setup Details}

RTAB-Map was evaluated in stereo frame-to-map odometry mode using the \texttt{rtabmap\_ros} package under ROS2 Jazzy. Camera images were first rectified via two \texttt{image\_proc/rectify} nodes and camera info published by a custom \texttt{euroc\_caminfo\_pub.py} node. The \texttt{stereo\_odometry} node performed visual odometry using GFTT feature detection and FLANN-based matching, while the \texttt{rtabmap} node performed global SLAM with appearance-based loop closure via a bag-of-words index. All sequences were replayed from \texttt{.db3} ROS2 bags without time manipulation (\texttt{bag\_rate: 1.0}); frame dropping is therefore possible when processing exceeds the 50\,ms / 20\,Hz budget.

In this plot, we observe the front-end latency when running OV2SLAM on each sequence. The lowest latency always comes from the Fast configuration and it has the least standard deviation compared to the Accurate mode. The least possible total front-end latency is around 5ms which corresponds to 200 Hz in Fast mode, while the Accurate mode has a least possible total front-end latency of around 15ms, which is 66 Hz.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{images/ov2_process_cpu_by_sequence.png}
\caption{OV$^{2}$SLAM mean process CPU utilization by sequence.}
\label{fig:ov2_cpu}
\end{figure}
From this plot, we observe that Accurate mode consistently uses significantly more CPU than Fast mode across all sequences. Accurate mode can reach up to 250\%+ CPU utilization and even higher due to the sudden utilization spikes by the Loop Closure threads. In contrast, Fast mode has much lower CPU utilization and can typically run in \lt 2 cores, though 2 cores would be ideal. This shows that while Accurate mode maximizes estimation accuracy, it comes at a significant cost for edge devices, compared to Fast mode which can have reasonably closer accuracy and much lower latency (3x times reduction in front-end delay)

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{images/ov2_role_means.png}
\caption{OV$^{2}$SLAM logical thread-role utilization: accurate vs fast.}
\label{fig:ov2_roles}
\end{figure}
From this plot, we observe that CPU usage in Accurate mode is dominated by the estimator thread, which is responsible for performing local bundle adjustment. The second most computationally intensive thread is the loop closure thread, which adds a substantial amount of CPU consumption on top of the existing processing threads. In contrast, Fast mode shows significantly lower CPU usage across all threads, reflecting its lightweight design. This reduction in computational load supports the idea that Fast mode is more suitable for edge devices while still maintaining high processing speed.

A critical observation is that the mean odometry estimation time \textbf{consistently exceeds 88--104\,ms across all sequences} (std $\approx$\,25--30\,ms, P95 = 133--162\,ms), which is \textbf{more than double the 50\,ms budget} imposed by the 20\,Hz stereo stream. This means that RTAB-Map's \texttt{stereo\_odometry} cannot process every incoming frame in real time on the Raspberry Pi 5. With \texttt{always\_process\_most\_recent\_frame = false}, the node queues incoming frames, gradually accumulating a backlog. The effective odometry processing rate was verified directly from the \texttt{/odom\_info} timestamps recorded during each run: the node processes at \textbf{8.4--10.5\,Hz} across all sequences, roughly half of the 20\,Hz input rate. This means approximately every other frame is eventually processed, with increasing temporal lag relative to the camera. This frame lag introduces growing misalignment between the motion model and the actual camera trajectory, which is the primary contributor to the elevated RMSE on the more dynamic and difficult sequences.

The P95 processing time (133--162\,ms) is especially important: it means that at peak load, a single odometry call takes over 3$\times$ the frame budget, causing the backlog to deepen temporarily. These spikes coincide with keyframe creation events where the local bundle adjustment (orange bars, mean 8--26\,ms, std 11--18\,ms) runs on top of the feature estimation, as seen from the wide standard deviation of the local bundle time.

\section{Conclusions}

While OV$^{2}$SLAM was benchmarked to the best of my ability, ORB-SLAM3 presents a significant challenge, particularly because it is not available on the official ROS GitHub and is unstable during runtime. My hypothesis is that
\begin{itemize}
    \item \textbf{Hypothesis 1: Pipeline Latency.} The rosbag adapter publishes stereo frames at real-time rate (\texttt{playback\_rate: 1.0}), but ROS2 topic transport and subscriber callback overhead MAY have introduced sufficient latency that by the time each stereo pair reaches the ORB-SLAM3 tracking thread, the subsequent frame has already been published. The bounded stereo buffer (maximum 20 frames per channel) then makes non-deterministic keep/drop decisions under load, causing different frames to survive across runs and producing run-to-run RMSE variability.

    \item \textbf{Hypothesis 2: Tracking Budget Exceeded.} The ORB-SLAM3 tracking thread exceeds the 50\,ms per-frame budget imposed by EuRoC's 20\,Hz stereo input. When per-frame tracking time surpasses this threshold, the pipeline accumulates a backlog faster than it can be consumed. The bounded buffer subsequently drops frames non-deterministically depending on OS thread scheduling, causing divergent map evolution paths and unstable trajectory estimates across repeated runs.
\end{itemize}

\subsection*{Five-way summary (see Tables~\ref{tab:master_comparison_rmse} and~\ref{tab:master_comparison_frontend} for full numbers)}

RTAB-Map presents a well-integrated ROS2 pipeline and completed every run without crashing — a key advantage over ORB-SLAM3. The system is limited primarily by hardware: the stereo odometry pipeline takes 88--104\,ms per frame (P95 up to 162\,ms), more than double the 50\,ms budget at 20\,Hz. The effective processing rate was verified from \texttt{/odom\_info} timestamps at \textbf{8.4--10.5\,Hz} — roughly every other frame is processed with growing temporal lag.

\paragraph{RMSE comparison (averaged across valid runs).}
\begin{itemize}
    \item \textbf{OV$^2$SLAM Accurate} achieves the lowest average RMSE (mean $\approx$\,0.066\,m), tracking all sequences reliably with results close to its published paper values.
    \item \textbf{OV$^2$SLAM Fast} is worse than Accurate on harder sequences (mean $\approx$\,0.106\,m excl.\ V1\_03) and catastrophically fails on \textcolor{red}{V1\_03\_difficult} (0.670\,m).
    \item \textbf{ORB-SLAM2} (three runs per sequence, batch \texttt{20260530\_232822}) averages $\approx$\,7.2\,cm RMSE with low run-to-run spread, completes all sequences, and uses $\approx$\,172\% CPU with $\approx$\,48\,ms frontend time — similar cost to ORB-SLAM3 but far more stable here.
    \item \textbf{ORB-SLAM3} delivers competitive best-run results on sequences it completes (0.039--0.247\,m), but shows severe instability: it fails entirely on \textcolor{red}{V2\_01\_easy} (n/a), produces 0.331\,m on \textcolor{red}{V1\_02\_medium}, and has high run-to-run variability (average across successful sequences $\approx$\,0.139\,m). Unlike RTAB-Map, its failures are not always detectable from pose count alone.
    \item \textbf{RTAB-Map} has the highest mean RMSE ($\approx$\,0.154\,m) but is the only system completing all sequences. It beats ORB-SLAM3 on \textcolor{red}{V1\_02\_medium} (0.081 vs.\ 0.331\,m) and MH\_03\_medium (0.146 vs.\ 0.247\,m). Its failure mode — early tracking loss producing a low pose count — is easy to detect and flag automatically.
\end{itemize}

\paragraph{Frontend/odometry latency comparison.}
\begin{itemize}
    \item \textbf{OV$^2$SLAM Fast}: $\approx$\,5\,ms mean — the fastest, comfortably within the 50\,ms budget.
    \item \textbf{OV$^2$SLAM Accurate}: $\approx$\,16--22\,ms mean — still well within the 50\,ms budget.
    \item \textbf{ORB-SLAM3}: $\approx$\,32--52\,ms mean — at or slightly above the budget, causing non-deterministic frame drops.
    \item \textbf{RTAB-Map}: \textbf{88--104\,ms mean} ($\pm$25--30\,ms std, P95 up to 162\,ms) — consistently over 2$\times$ the budget, forcing operation at 8.4--10.5\,Hz.
\end{itemize}

\paragraph{CPU utilization comparison.}
\begin{itemize}
    \item \textbf{OV$^2$SLAM Fast}: $\approx$\,43--52\% mean — the lightest, easily fitting in a single core.
    \item \textbf{RTAB-Map}: $\approx$\,120--135\% mean — uses just over one full core; the most CPU-efficient \emph{complete SLAM system} evaluated.
    \item \textbf{ORB-SLAM3}: $\approx$\,87--150\% mean — similar to RTAB-Map but less stable.
    \item \textbf{OV$^2$SLAM Accurate}: $\approx$\,141--165\% mean — highest average CPU of the four, driven by its local bundle adjustment and loop closure threads.
\end{itemize}

\paragraph{Overall assessment.} On a Raspberry Pi 5, OV$^2$SLAM Fast is the clear winner for edge deployment: lowest latency, lowest CPU, and acceptable accuracy. OV$^2$SLAM Accurate is the best choice when accuracy matters and CPU budget allows $\approx$1.6 cores. RTAB-Map's odometry is too slow for 20\,Hz real-time operation on this hardware but its failure mode is graceful and its loop closure can partially compensate for drift. ORB-SLAM3 remains the least suitable due to non-deterministic instability.

\subsection{Comparison summary}

\begin{itemize}
  \item \textbf{Accuracy:} OV$^2$SLAM Accurate still has the lowest typical RMSE; ORB-SLAM2 is next-best among systems that always finish ($\approx$7\,cm mean on easy MH, up to $\approx$13\,cm on \textcolor{red}{V1\_03}). ORB-SLAM3 can beat everyone on a lucky best run but fails or spikes on several sequences.
  \item \textbf{Speed:} OV$^2$SLAM Fast ($\approx$5\,ms) is the only mode clearly inside the 20\,Hz budget. ORB-SLAM2 and ORB-SLAM3 sit near or above 50\,ms. RTAB-Map is slowest ($\approx$88--104\,ms).
  \item \textbf{CPU:} OV$^2$SLAM Fast uses $<$0.5 core. RTAB-Map and ORB-SLAM2/3 use $\approx$1.3--2 cores. OV$^2$SLAM Accurate is heaviest when loop closure runs.
  \item \textbf{Reliability:} ORB-SLAM2 and RTAB-Map completed every sequence in their batches; ORB-SLAM3 missed \textcolor{red}{V2\_01} and often needed cherry-picked best runs.
\end{itemize}

\paragraph{Why ORB-SLAM3 fails more than RTAB-Map despite being faster per frame.}
ORB-SLAM3's descriptor matching can fail abruptly under backlog, while RTAB-Map's flow-based odometry degrades more softly — see per-algorithm sections for detail.
