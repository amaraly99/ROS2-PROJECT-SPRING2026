## Symptom

OV2SLAM (fixed to build/run at all in FIX-018) runs fine but its own startup
log reveals a silent degraded path:
```
OPENGV NOT FOUND!  OPENCV MVG FUNCTIONS WILL BE USED!
```
`Thirdparty/opengv/build/` (present since FIX-018's Thirdparty copy) already
contains compiled `libopengv.a`, `librandom_generators.a`, and a generated
`opengvConfig.cmake` -- opengv is fully built, just never found.

## Root cause

`src/ov2slam_ros/CMakeLists.txt` (verified by reading it directly) finds
Ceres and Sophus by pointing `find_package()` explicitly at their own local
`Thirdparty/` build/install dirs:
```
find_package(Ceres  NO_DEFAULT_PATH PATHS ${PROJECT_SOURCE_DIR}/Thirdparty/ceres-solver/install/)
find_package(Sophus NO_DEFAULT_PATH PATHS ${PROJECT_SOURCE_DIR}/Thirdparty/Sophus/build/)
find_package(opengv QUIET)   # <- the only one of the three with no PATHS hint
```
opengv's line never got the same treatment, so it only ever resolves via
CMake's default system search paths -- which come up empty (no
`opengvConfig.cmake` anywhere under `/usr/local` in the actual runtime
container). Confirmed this predates tonight entirely: the binary copied from
`feat/stereo-hil` in FIX-018 (unmodified source) has the same "NOT FOUND"
string baked in -- this is a pre-existing upstream/vendored gap, not
introduced by the migration.

## Diff

One line, `src/ov2slam_ros/CMakeLists.txt`, mirroring the exact pattern
already used for Sophus two lines below it:
```diff
-find_package(opengv QUIET)
+find_package(opengv QUIET NO_DEFAULT_PATH PATHS ${PROJECT_SOURCE_DIR}/Thirdparty/opengv/build/)
```
Then `./run_stack_hil.sh build ov2slam` (this repo's own colcon-in-a-
throwaway-container build path). Scope: `ROS2-slam-hil` only -- did not touch
`feat/stereo-hil`'s copy of the same file, even though the same gap almost
certainly exists there too.

**Two more gaps surfaced while actually running the rebuild** (neither
predicted by either review agent, found live):
1. Rebuilding `ov2slam` from source for the first time on this worktree hit
   `fatal error: opencv2/xfeatures2d.hpp: No such file or directory` in
   `feature_extractor.cpp`. Root cause: the custom OpenCV 4.10 build (copied
   in FIX-018 for *runtime* linking) needs its contrib module SOURCE headers
   at *compile* time too, and those live in a completely separate sibling
   directory, `opencv_contrib/` (155 MB, confirmed via
   `OPENCV_EXTRA_MODULES_PATH:PATH=/workspace/opencv_contrib/modules` in the
   OpenCV build cache) -- never copied in FIX-018 because FIX-018 only
   verified *runtime* linkage (`ldd`), which doesn't touch header search
   paths at all. Fixed: `rsync -a` `opencv_contrib/` from `feat/stereo-hil`
   the same way `opencv/` was copied.
2. After copying `opencv_contrib/`, the rebuild failed identically and
   *faster* (17.6s vs 57.1s) with no CMake configure-stage output at all --
   colcon reused the stale `flags.make` generated by the FIRST failed build
   attempt (before `opencv_contrib` existed), rather than reconfiguring.
   Fixed non-destructively (no deletion, per this session's standing rule):
   ran the same `docker run --rm ... colcon build` invocation directly with
   `--cmake-force-configure` appended, which `run_stack_hil.sh build` doesn't
   expose as a passthrough flag.

## Critic verdict & concerns

**open_concern**, proceeded per protocol. Verified the diff was accurate by
reading the live file. Raised: opengv's exported CMake target only defines
`IMPORTED_LOCATION_RELEASE` (no plain/DEBUG variant) -- if `ov2slam`'s colcon
build didn't force `CMAKE_BUILD_TYPE=Release`, this could turn today's clean
fallback into a linker error instead. Checked directly before applying:
`CMakeLists.txt:24` hardcodes `set(CMAKE_BUILD_TYPE "Release")`
unconditionally, independent of what colcon passes -- concern resolved,
confirmed not applicable here.

## KISS verdict

**simple.** Simplification agent confirmed no lighter-weight alternative
exists: grepped `run_stack_hil.sh`, every `Dockerfile` in the repo, and
`scripts/` for any existing `CMAKE_PREFIX_PATH`/`opengv_DIR` convention to
extend -- zero hits. Installing opengv to `/usr/local` (system-wide) was
considered and rejected: the build runs inside a `--rm` throwaway container,
so anything written outside `/workspace` (the only bind mount) is lost the
instant the container exits -- confirmed via `run_stack_hil.sh:409-416`.

## Verification

- `strings` on the newly-built binary: was `OPENGV NOT FOUND!  OPENCV MVG
  FUNCTIONS WILL BE USED!`, now `OPENGV FOUND!  OPENGV MVG FUNCTIONS WILL BE
  USED!` -- and the binary is now full of real `opengv::` namespace symbols
  (`absolute_pose::modules::p3p_kneip_main`, `relative_pose::modules::
  fivept_nister`, etc.), confirming actual static linkage, not just a string
  change.
- Restarted `slam_ov2slam`, waited 25s: `RestartCount=0`, `Status=running`.
- Log tail from this restart specifically (the container's log file
  accumulates across restarts, so earlier "NOT FOUND" lines from before the
  fix are still visible above it): `OPENGV FOUND!  OPENGV MVG FUNCTIONS WILL
  BE USED!` immediately followed by `OV²SLAM is ready to process incoming
  images!` -- clean startup on the fixed path.
- `ldd` on the binary (real launch `LD_LIBRARY_PATH`): zero `not found`
  entries.
- Noted, not chased: the rebuild produced linker warnings about
  `libopencv_*.so.406` (system, pulled in transitively via ROS2's `cv_bridge`)
  possibly conflicting with `libopencv_*.so.410` (the custom build ov2slam
  itself links against). Warning only, not an error, and RestartCount stayed
  0 through a real restart -- but flagged as TODO-AG since it's exactly the
  kind of thing that can cause a much harder-to-diagnose issue than either of
  today's two failures if it ever bites (e.g. wrong symbol version resolved
  at runtime under different load order).
